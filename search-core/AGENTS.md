# search-core

## Purpose
Owns: business logic for searching text inside files — settings/models, matching, text extraction (TXT/DOCX/PPTX/XLSX/ZIP/RTF/PDF, optional OCR), robust async file I/O, incremental caching, HTML/CSV/JSON/JSONL reporting, parallel orchestration, and the policy layer over the `native-search` fast-index crate.
Does not own: any GUI (`app/`, `app-egui/`), CLI parsing (`cli/`), or `native-search`'s own indexing internals (`native-search/src/engine.rs`) — this crate only calls that engine in-process.
Plain Rust library, zero GUI dependency — `cargo test -p search-core` must build/pass with no GUI toolchain present (a 1:1 port of the removed C# `TextInFilesSearch.Core`; see `docs/rust-rewrite-status.md`; fixtures in `test-data/`, report banner in `assets/`). Never add a dependency that pulls in Dioxus, egui, or any windowing toolkit.

### Key Relationships
`file_reader` (enumerate/read) → `extraction` (bytes→lines) → `matching` (lines→hits) → `orchestrator` (drives all three in parallel, writes `cache`/`failure_log`) → `report` / `native_index` (consume results). `regex_literals` feeds only the candidate-filter path in `orchestrator`/`native_index`, never `matching` directly. `ocr` is called only from inside `extraction::extract_pdf_lines` — extraction owns all PDF-format knowledge.

## Design Rationale
- **Problem solved**: correct whole-word/regex matching across TXT/Office/PDF with live per-file progress on slow files, fast enough for 100k+ file trees.
- **Core insight**: `fancy-regex` (not `regex`) for *every* match mode, including plain literal-mode compilation, so whole-word lookaround (`(?<![\p{L}\p{N}_])...(?![\p{L}\p{N}_])`) is available uniformly — `regex` has no lookaround by design. One engine for all modes avoids two engines' semantics quietly diverging on edge cases (e.g. `"C#"` standing alone between spaces).
- **Constraint**: DOCX/PPTX/XLSX/ZIP extraction mirrors the C# original's dependency-free approach (`zip` + regex tag-stripping), not a real OOXML parser — a "better" library would extract differently on edge cases and silently drift from the byte-for-byte-tested original. Same reasoning for PDF's hand-rolled stream/ASCII85/FlateDecode walker.

## Contracts
- `InFlightMap` (`orchestrator.rs`) is `std::sync::Mutex`, not `tokio::sync::Mutex` — the PDF-progress/retry-status callbacks in `extraction.rs`/`file_reader.rs` are plain sync `FnMut`, not async. Live per-file progress is a hard requirement (app exists because the legacy PowerShell tool's PDF processing went silent for seconds with no way to tell "still working" from "stuck"): any change to `orchestrator.rs`/`extract_pdf_lines` must preserve the ~150ms PDF progress callback, the background `ticker_handle`, and per-file in-flight status — don't collapse into a simpler start/done model, and don't "upgrade" the mutex without also making the callbacks async.
- `matching::LineMatchOutcome.passes_mode` must stay an explicit struct field, never re-derived from `hits.is_empty()` — a prior version conflated "no hits at all" with "hits existed but failed AllInFile/Proximity gating" (see `orchestrator.rs:610`).
- `is_excluded_directory` (`file_reader.rs`) matches `exclude_folders` by whole path segment (case-insensitive), never substring — `bin` must not exclude `cabinet/`.
- `read_zip_entry_to_string` and `inflate_raw_deflate` (`extraction.rs`) must stay size-bounded (`Read::take`), independent of the orchestrator's `max_file_size_mb` gate — that gate only sees on-disk *compressed* size. Fixed after an audit found the single choke point every DOCX/PPTX/XLSX XML read goes through had no size check at all (commit `049820b`, epic #6 §62).
- `regex_literals::required_literal_chunks` must return `None` (never narrow) on any syntax it isn't fully sure about — a wrong chunk silently drops real matches, worse than not narrowing. Bounded quantifiers (`{n}`,`{n,}`,`{n,m}`) are the one deliberate exception (commit `a07bfd8`).

## Patterns

### Fixing a PDF text-extraction gap
1. Confirm the content stream is located/decompressed (`find_stream_blocks`) before assuming the matching regex is wrong.
2. Check both operand shapes: `text_re` (parenthesized-literal `Tj`/`TJ`) vs `hex_string_re` (hex-string — the *default* for headless-Chromium print-to-PDF, invoicing tools, LaTeX, not a rare edge case).
3. Hex-string operands must resolve through the file's own `/ToUnicode` CMap (`parse_tounicode_cmap`) — never treat a raw CID as a Unicode codepoint (produces wrong text, not just missing text; real bug, commit `3c4f94c`).
4. Concatenate all hex-derived chars within one content stream into a single line before pushing — some generators emit one `Tj` per glyph, fragmenting every word into single characters and silently breaking whole-word/substring search even with byte-correct text (same commit).
5. Add a fixture-backed test in `tests/fixtures.rs` reproducing the exact operand shape.

### Adding a new file-format extractor
1. Add extension(s) to `models.rs::extension_catalog::CATEGORIES` — single source of truth for both the engine's default list and the UI picker.
2. Implement in `extraction.rs`, following the existing "skip what isn't confidently handled, never guess" convention.
3. Add a real fixture (reused from the C# test harness where possible) and a case in `tests/fixtures.rs`.
4. Update `orchestrator::is_heavy_extension` if the format warrants the separate heavy-throttle semaphore (`heavy_throttle_limit` vs `throttle_limit` are independent semaphores, so light/heavy file mixes don't starve each other).

- **Semantic retrieval is hybrid** (`lexical.rs`, `semantic_index::search_filtered`): short queries (<= `MAX_QUERY_TERMS` distinct terms) fuse cosine rank with BM25 rank (RRF, lexical weight 2.0) so bare numbers, spec codes and part numbers (`M8` finds `M8x1.25`) are found; longer queries (related-document discovery) stay dense-only. `SemanticHit::similarity` stays the cosine value; only order changes, and `evidence::select_evidence` still sorts selected passages by cosine. The scan keeps compact per-chunk counts (memory is proportional to chunk count for fused queries, not `limit`). Guarded by `fused_ranking_beats_dense_only_on_the_hard_retrieval_set` (40-question set in `search-ml/examples/data/retrieval_eval.tsv`; dense 34/40 -> fused 37/40; synthetic, so confirm on real documents before retuning).
- **Semantic index stamp**: `semantic_meta.embedding_version` = `search_ml::EMBEDDING_MODEL_VERSION` (1 = MiniLM-L6-v2 fp32). `SemanticIndex::open` deletes all stored vectors on mismatch, so documents re-embed on the next build. Bump the constant in `search-ml` whenever the embedding weights, pooling or normalisation change (e.g. an int8 swap); guarded by `embedding_model_version_mismatch_discards_stored_vectors`.
- **Index freshness is `(modified in ns, size)` per document; a content hash is checked only on request** (`native_index.rs`, `cache::ticks_from_modified`; no filesystem watcher). Each document also stores the SHA-256 of the bytes it was indexed from (`content_hash`, written by both file-index writers; the fast-re-search writer stores one only when the file's time and size are unchanged before and after hashing). `native_index::verify_content` reads every indexed file once, drops the ones that differ (or have no hash) from the index and `semantic.sqlite`, and returns `ContentCheck` (`changed`, `hidden` = changed with the same time and size); the next update re-reads them. The Search window's Index card has a `Verify content` button (`Effect::BuildIndex { verify_content }`, `IndexStage::Verifying`). Nothing runs it automatically, so a same-size edit that restores the original mtime, or one made inside a coarse timestamp tick, stays invisible to searches until the check is run (a racily-clean rule needs a per-document index time, a schema change: not adopted, `docs/search-benchmarks.md` item 9). Changing what the index stores or how text is extracted/normalised means bumping `INDEX_SEMANTIC_VERSION` (7 now; stamp file in the index folder; mismatch rebuilds on open).
- `build_or_update_corpus_index` keeps a sliding window of extractions in a `JoinSet` and indexes in completion order - do not go back to awaiting a fixed window in order (one slow file stalled its whole window; measured in `docs/index-audit-2026-10.md`).
- `CorpusIndexOutcome.failed_files` is capped (`MAX_FAILURE_DETAILS`); use `failed_count` / `failure_summary` for totals.
- Index metadata that cannot be read must never be treated as an empty index (`read_known`).
- `remove_orphaned_documents` is global and must keep per-id `exists()`: an id outside the current scan scope may be merely excluded by settings. `narrow_candidates` already subtracts the scope first.

- **Exact-match speed path (2026-11-10)** (`matching.rs`): in literal and whole-word modes with all-ASCII filters, `ascii_prefilter` (one case-insensitive regex over all filters) rejects non-candidate lines before any lowercasing; it is skipped for lines containing U+0130 (the only non-ASCII char whose lowercase holds ASCII that `(?i)` does not match; U+212A is matched by both), proved by `lowercase_to_ascii_sources_are_only_kelvin_and_dotted_i`. Whole-word on an ASCII line decides word boundaries by hand (`whole_word_ascii`, differential test against the lookaround regex) instead of running the lookaround regex once per filter. Measured on 150k lines: literal 437 -> 71 ms, whole word 5236 -> 181 ms. Do not "simplify" these back into the regex path. Literal mode with filters that match most lines (2026-11-16): the cost was Unicode `to_lowercase` on every passing line, not the prefilter, so a line with neither U+0130 nor U+212A is compared through an ASCII-lowercased copy in a reused buffer (exact by the same code-point proof), and the prefilter is skipped per 32-line window while more than half the lines hit (`PrefilterUse::Adaptive`; `CompiledMatchState::prefilter_pays` carries the last state to the next file, speed only). `prefilter_policies_return_identical_hits` holds always-on, always-off and adaptive to the reference definition. Keep per-line bookkeeping out of the line loop: per-line window counters cost the rare-filter rows about 6 % (measured), which is why the decision reads the hit-list length at window boundaries.
- **Opt-in folding and typo tolerance**: `SearchSettings::fold_accents` (literal and whole-word only) compares `textfold::fold_lower` of line and filter; `typo_tolerance` (1 or 2) adds `FuzzyFilter` word matches after the exact check (words under 4 letters or with digits stay exact; excludes never fuzzy). Both feed `cache::compute_fingerprint` (skipped at defaults) and differ in narrowing: `typo_tolerance` makes `native_index::narrow_candidates` return no candidates (words that differ from the filter bound no trigram set), while `fold_accents` narrows through the `trigram_folded` field (written by every file-index writer through `native_index::folded_trigram_text`, only for a document whose folded text differs from its lowercased text; the query is the raw trigrams OR the folded ones of the folded filter; `tests::folded_narrowing_keeps_every_file_the_folding_matcher_finds`). A new writer of the file index must pass `folded_trigram_text` or folded searches lose that document. Highlighting must use `explain::LineExplainer`, not a plain substring search.
- **OCR flag of the fast index (`native_index.rs`)**: the index directory holds an `ocr-pdfs` stamp (`1`/`0`, written when a build finishes) because the per-file (modified, size) check cannot see a settings change. Turning OCR on re-extracts every PDF once on the next build; until then `narrow_candidates` counts each PDF as stale (`needs_update`, so `NarrowOutcome::is_stale` shows the update hint) and scans it directly, so scanned PDFs are not missed. Test: `turning_ocr_on_re_extracts_pdfs_once_and_leaves_other_files_alone`.
- **Result cache hardening (`cache.rs`, `orchestrator.rs`)**: entries are dropped on load when their mtime is within 2 s of the cache's own `saved_at_ns` (git's "racily clean" rule; coarse mtimes + same size could otherwise hide an edit), and `ReadError`/`UnexpectedError` entries are never reused (a locked-file error was replayed until the file was next modified). `max_embed_lines`, `fold_accents`, `typo_tolerance` join the fingerprint at non-default values.
- **`regex_literals`**: an escape with operand characters (`\x41`, `\pL`, `\1`, `\u{..}`, `\k<n>`) now bails; before, the operand characters (`41`, `L`) were kept as required literal text and would have dropped real matches. Plain character classes now break the run like `.`; top-level `a|b` becomes OR'd chunk sets (no groups). Guarded by a test that checks every chunk set against real regex matches.

- Run `cargo test -p search-core` before considering any change done — must build without the `ocr` feature or any GUI crate present.

## Pitfalls
- PDF hex-string/CID-font PDFs silently produced zero text (default encoding for most modern generators, not an edge case) *and*, separately, could fragment every word into single characters even after that fix — both real bugs, both from commit `3c4f94c`. See Patterns above before touching PDF extraction.
- fancy-regex's combined candidate pre-check fails OPEN (`unwrap_or(true)`) while the authoritative per-filter check fails CLOSED (`unwrap_or(false)`) on the 1,000,000-step ReDoS backtrack limit — a pathological filter silently reports "no match" on the line it choked on rather than erroring the whole search (`matching.rs` module doc, verified commit `a07bfd8`).
- `zip`'s `xz` feature is deliberately disabled workspace-wide (native `links="lzma"` conflict elsewhere in the workspace) — an XZ-compressed ZIP entry now silently extracts *less* text (that entry skipped) instead of erroring; never more. Check compression method first if content goes missing from a DOCX/XLSX.
- `.native-search-index/` lives inside the searched folder (ADR-011) — `ensure_index_folder_excluded` must run before every walk or the index self-indexes. Commit `6439980`: indexing was succeeding but its status message went to a collapsed `<details>` panel nobody had expanded, making working indexing look broken — check status routing, not just the indexing logic, when "indexing isn't working" is reported.
- Literal (non-regex, non-whole-word) mode deliberately bypasses `fancy_regex` entirely via plain lowercase `str::contains` (`filters_lower`) — looks inconsistent with "one engine for all modes" above, but was a real perf fix for a "large-folder search slower than the old PowerShell tool" regression. Don't route literal mode back through regex compilation.
- `nl_find` labels files "all matched" / "one weak" (needs 3+ wanted conditions) / "partial", never a percentage, and judges only the 10 best-ranked candidate files with 2 passages per (file, condition): a file with no hit for a condition inside the top-100 retrieval is unconfirmed, not judged. The language model is ~9 s per judge call on an 8 GB M1 CPU, which is why the cap exists. Language-model prompts, grammars and the quote check live in `search-llm/`; its judge grammar must keep the model's natural spacing (`{ "quote": ...`): a compact `{"quote":` grammar made Qwen3-4B emit a garbled quote (issue #0128). The model never indexes or OCRs: OCR is `ocrs`+`rten` in `ocr.rs`, embeddings are MiniLM in `search-ml`.
- **PDF/OCR line quality** (`line_quality.rs`, `docs/search-ocr-line-quality.md`): `extract_pdf_lines_capture` joins each `TJ` array into one line (`join_tj_array`), scans only streams that are at least 60% printable ASCII (`looks_like_content_stream`), then `line_quality::clean_lines` repairs Windows-1252 and Computer Modern ligature codes and drops lines with no plausible content, keeping the parallel `origins` vector aligned; OCR lines go through it per page as `Source::Ocr`. It runs before the OCR-fallback check so an all-junk text layer falls through to OCR. Bias is toward keeping: a line survives on one word-like, numeric or part-number token. Guarded by the keep and drop sets in `line_quality::tests` and `test-data/line-quality-labels.tsv`. Changing what it drops means bumping `native_index::INDEX_SEMANTIC_VERSION`, `semantic_index::CITATION_VERSION` and `cache::EXTRACTION_VERSION`. MiniLM measured useless for this and the language model is far too slow per line (see the doc); do not add a per-line model call.

- **PDF line cleaning joins soft-hyphen line breaks** (`line_quality::join_soft_hyphens`, called at the end of `clean_lines`): a line ending in U+00AD absorbs the next line, keeping the first line's page origin. Changing it changes stored text, so bump `native_index::INDEX_SEMANTIC_VERSION`, `semantic_index::CITATION_VERSION` and `cache::EXTRACTION_VERSION` together (all three were raised on 2026-11-08).
- **Ordinary hyphen breaks are repaired from the document's own words** (`line_quality::dehyphenate`, after `join_soft_hyphens`): a line ending `letters-` followed by a line starting with lowercase letters becomes `understanding` / rest-of-line only when the joined word appears whole elsewhere in the same document and the hyphenated compound (`pre-training`) appears nowhere; lines with different PDF origins (a page break) are never joined, the fragment's trailing `.,;:)]!?` moves with it, line count and page citations are unchanged. Measured on `benches/data/xlarge.pdf`: 2315 hyphen-ended lines, 1495 repaired, 23392 -> 23376 lines. Raised `cache::EXTRACTION_VERSION` to 3, `native_index::INDEX_SEMANTIC_VERSION` to 5, `semantic_index::CITATION_VERSION` to 4.
- **Extraction settings are part of cache and failure identity.** `cache::compute_fingerprint` includes `ocr_scanned_pdfs` and `pdf_timeout_seconds` (omitted at their defaults, so old caches stay valid); `failure_log::FailureLog::open_with_context(path, extraction_context(&settings))` stores a context number beside each failure (`(pdf_timeout - 15) << 1 | ocr`) and `known_failure_reason` only matches the same context, so turning OCR on or raising the PDF timeout retries files that failed before. Old databases gain the column on open. The `native_index` stamp (path, size, time) does not include the OCR setting: a PDF indexed without OCR is not re-extracted when OCR is switched on (not changed here).
- **OCR runs page by page and is cached** (`extraction.rs` OCR fallback, `ocr.rs`): image streams are decoded one at a time in file order (`jpeg_image_from_stream`, `raw_flate_image_from_stream`) with a timeout check and a progress callback before each page; decoding all pages first held every page's pixels at once and stayed silent. `ocr::cache_key` is a SHA-256 of the stream dictionary and bytes (plus model sizes and `OCR_CACHE_VERSION`); recognised raw lines (before `line_quality`) are kept in memory and, when `SearchSettings::ocr_cache_dir` is set (`extraction::configure_ocr_cache`, called by the orchestrator), in `<dir>/<key>.txt`. OCR is still only attempted when the text layer has no lines at all; on the scanner path a PDF mixing text pages and scanned pages is not OCR'd. Under `pdf-yolow` (`pdf_yolow.rs`) it is: with OCR on, `BundledOcr` (`ocr::ocr_gray_boxes`, line boxes in the given image's pixels) is yolowpdf's `PageOcr`, so a page without a text layer inside a text document is recognised and keeps its page number (test `a_scanned_page_inside_a_text_pdf_is_recognised_with_its_page_number`, fixture `test-data/mixed-text-scan.pdf` from `scripts/make_mixed_scan_pdf.py`; yolowpdf calls a document scanned when half its pages are, so the whole-document scanner fallback still handles those). That path has no recognised-text cache and indexes built before it keep the old text for such PDFs until the file changes. **OCR confidence** comes from a vendored `ocrs` 0.12.2 (`../third_party/ocrs`, path dependency; the only change is `TextChar::confidence`, the model's probability for each character, see its `NOTICE.md`). `ocr::ocr_gray_lines` returns `OcrLine` (box, text, `char_confidence`, `mean_confidence()`); `OcrScore` sums probabilities and characters per page and per document, and the OCR cache is version 3 (`#ocr3 <p_sum> <chars>` header, older files are a miss). `ExtractedLines`/`PdfExtraction.ocr_confidence` carry the document mean to `FileSearchResult.ocr_confidence` (`None` = no OCR text or unknown: fast-index results, entries cached before `cache::EXTRACTION_VERSION` 5). Under `pdf-yolow` `BundledOcr` accumulates the score and now sets `ocr_used` when pages were OCR'd inside a text PDF (before, such PDFs were not flagged). `models::POOR_OCR_CONFIDENCE` = 0.97 splits the label (`pdf_warning`: "OCR 98%: may be misread" / "OCR 62%: poorly read"; `pdf_warning_detail` for the detail note; the HTML report note quotes it too). The warning itself stays on every OCR PDF: even clean generated pages read about 3% wrong, so a high score never clears it. The score is the model's own certainty, not accuracy, and does not see text the detector missed. Calibration (80 generated scan pages, 16 degradations): page-level AUC 0.988 for pages with more than 5% wrong characters; at 0.97 every flagged page was bad (100% precision) and 88% of bad pages were flagged; details, line-level numbers and caveats in `docs/search-benchmarks.md` ("OCR confidence"). Synthetic text only: real scanners, CCITT scans and Windows were not run. Harness: `python3 scripts/make_ocr_confidence_set.py OUT_DIR`, then `cargo run -p search-core --release --features ocr --example ocr_confidence_eval -- OUT_DIR` (about 10 minutes). Vendored crate tests: `cargo test --release --manifest-path third_party/ocrs/Cargo.toml` (it makes `third_party/ocrs/target` and `Cargo.lock`; delete both, they are not committed). Not adopted: dropping recognised lines with mean probability under about 0.6 (spurious lines, mostly specks read as text, average 0.41; matched lines that low average 0.93 character error) because it changes indexed text and needs `retrieval_eval` first.
- **Page provenance** (`pdf_page_map.rs`, feature `semantic-search`): `page_by_stream_offset` tries the strict classic-xref reader first (refuses `/Prev`, `/XRefStm`, `/Encrypt`, object streams), then a `lopdf` fallback (`page_by_stream_offset_lopdf`) that reads cross-reference streams, object streams and `/Prev` chains: a page owns the body of its `/Contents` streams, found by matching `lopdf`'s loaded bytes against the file at the xref offset (`lopdf` drops `Stream::start_position` on load); a stream shared by two pages, a root `/Count` that disagrees with the leaves, or an encrypted file gets no page. Measured 2026-11-17 on the 27 ViDoRe source PDFs (scanner backend, `pdf_citation_bench`): before, 0 lines carried a page (every file uses xref streams); after, 111,229 lines carry one and 57,965 of 62,227 checkable lines (93.2%) cite the right page, 25 of 27 files mapped (`TO_35-1-18`, `TO_36-1-191` still none). Form XObject streams were tried and added one line, so they are not mapped. `real_large_pdf_keeps_bounded_page_numbers` (144-page `xlarge.pdf`) passes (release 1.8 s, debug 14 s); the classic mapper accepts that file, so the logged reject (#0127) could not be reproduced and was most likely a time-truncated extraction (the test now passes 300 s).
- **Natural-language Find retrieval and judging** (`nl_find.rs`, `lexical.rs`): keyword terms are stemmed (`lexical::terms`, blended = blending), each condition may carry a model-written `example` used only to retrieve, strong candidate files get up to 8 judged passages and weak ones 1, and when nothing is confirmed `Fit::Unconfirmed` closest passages are returned. See `docs/search-natural-language-find.md`.
- **Semantic queries run from an in-memory snapshot** (`semantic_cache.rs`): vectors, chunk lengths and term postings per index file, brought up to date when `semantic_meta.generation` changes: `Snapshot::updated` re-reads only the documents whose `semantic_documents.generation` stamp is newer than the snapshot and drops the ones no longer stored (a full `Snapshot::build` only when there is no snapshot of that database, identified by `semantic_meta.instance`). Every write path in `semantic_index.rs` must call `bump_generation` and stamp each document row it writes with the new value (`GENERATION_NOW`) in the same transaction; a path that forgets either serves stale results. Deletes need no stamp. The updated snapshot must equal a rebuilt one field for field (`incremental_snapshot_equals_a_rebuilt_one_through_adds_edits_and_deletes`). Indexes over `MAX_CACHED_CHUNKS` stream from SQLite instead (`search_streaming`); both paths must stay score-equivalent. Per-document freshness (`std::fs::metadata` per document per query) is still paid on every query.
- **Model calls are grouped by padded size** (`semantic_index::embed_calls`): the model pads each call to its longest text, so a call holds about one full chunk of padded text (`texts x longest <= CHUNK_CHARS`, at most `EMBED_BATCH`). Full chunks go one per call (45% faster than 16 per call), short ones together. Batch composition does not change a vector's bits (`batching_does_not_change_a_vector`), so this needs no `EMBEDDING_MODEL_VERSION` bump; inference is 97% of embed-and-store time and concurrent model calls gain nothing (`docs/search-benchmarks.md`, 2026-11-16).
- **Natural-language Find is rule-based** (`nl_rules.rs`, no model; the `search-llm` crate was removed 2026-11-08, backup of its uncommitted edits is not in git). `parse` only uses the sentence's own words; `judge` needs all key words in one or two neighbouring sentences, un-negated.
- **Retrieval knobs live in `lexical::LexicalConfig`** (stemming, fusion kind, keyword share, RRF constant, BM25 `k1`/`b`). `Default` is the benchmarked setting for passage retrieval over files (score fusion, keyword share 0.35); `LexicalConfig::rrf()` is the older rank fusion kept for the Search-help line ranking in `neural_search::best_lines`. Change a default only with numbers from `examples/retrieval_eval.rs` on all five benchmark sets (`docs/search-benchmarks.md`).
- **`ranking.rs` + `SemanticIndex::rank_features` are measurement-only**: raw per-chunk scores (similarity, BM25, length, place in file) with no extension/freshness filtering, used by `retrieval_eval --rank-experiments` (`examples/support/ranking_experiments.rs`) to score ranking ideas offline. Measured 2026-11-10 and not adopted (each loses on a benchmark set): query-length keyword share, file score = best chunk + decayed next chunks, learned linear fusion, near-duplicate removal (`evidence::select_evidence_with`, opt-in). A copied eval index folder with older path spelling duplicates every document; delete or rebuild it first.

- **The viewer's highlight offsets are UTF-16** (`viewer::HitSet::spans`), reader lines are decoded one at a time, `plan_for` checks the UTF-16 BOM before `looks_binary`, and the reader accepts only GET with a per-process token and a loopback `Host` (`viewer/reader.rs`, `docs/search-viewer.md`). Never serve a path the page names: the reader serves only files registered through `ReaderServer::register`.

## Re-embedding is skipped for unchanged text (2026-11-08)
`SemanticIndex::index_document_with_pages` stores a SHA-256 of the extracted lines and PDF pages (`semantic_documents.content_hash`). A file whose time or size changed but whose extracted text did not keeps its vectors and only takes the new stamp. That is still a write (counter bump and row stamp): the snapshot holds each document's time and size for the per-query freshness check, and without the bump it dropped the touched file's hits until some other write (`a_touched_file_with_unchanged_text_stays_in_cached_results`). Test: `unchanged_text_with_a_new_time_keeps_its_vectors`. Extraction still runs for such a file because the Tantivy index stores the stamp inside its documents; gating extraction on a file hash would need a stamp table or a Tantivy field and is not built. SHA-256 is enough: hashing extracted text is milliseconds against seconds of embedding (BLAKE3 measured about 5 times faster than the `sha2` crate here, which does not matter at that scale).

### Per-query cost and embedding reuse (2026-11-08)

- The snapshot search used to `stat` every indexed file on every query, one after another. The scope checks that need
  no file access (folder, hidden, size limit, extension) now run first from the indexed size, and one `stat` per
  remaining file runs across up to 8 threads (`semantic_path_listed` / `semantic_path_fresh`). Results are identical
  (SciFact nDCG@10 0.7518 before and after); only the per-query time drops, and it grows with the index.
- Re-indexing a file reuses the stored vector of every chunk whose text is unchanged
  (`SemanticIndex::stored_chunk_embeddings`); only new or edited chunks go through the model. Chunk boundaries are fixed
  every `CHUNK_CHARS`, so this pays off for appended text (logs, notes) and edits near the end; an insert near the top
  shifts every later boundary and re-embeds the rest. Whole-file reuse by content hash still comes first.
- A document whose extracted text equals another indexed document's (a copy, a renamed or moved file, a second
  revision folder) takes that document's stored chunk vectors (`SemanticIndex::donor_path`, looked up through the
  `semantic_documents_hash` index on `content_hash`, same `citation_version`); no model call. `open` now sets
  `PRAGMA foreign_keys = ON` outside the schema transaction (inside one SQLite ignores it); replacing or removing a
  document relies on the cascade to delete its chunks. Tests: `incremental_updates_embed_only_changes_and_leave_no_orphan_rows`
  (appended line, copy, replaced text, orphan cleanup, no stray chunk rows), `an_interrupted_build_resumes_without_redoing_finished_documents`.
  Build-time invalidation is `(modified, size)` via `is_current`, then the content hash inside
  `index_document_with_pages`; a file whose text changed within the same size and mtime is not seen (accepted, same as the
  exact index). Each document is one transaction, so an interrupted build keeps finished documents and the next run
  embeds only the rest.
- Chunking stays fixed 800 characters. Sentence/line/paragraph-boundary chunking (with and without 100-character
  overlap) lost to it on Cranfield and was not adopted; numbers in `docs/search-benchmarks.md` (lead merges). Do not
  retry without a different idea for what the boundary buys.
- No ANN index above `MAX_CACHED_CHUNKS`: the exact scan is cheap (about 35 ms for 250,000 chunks on one thread, 20 ms
  on 8); IVF needed 15% to 57% of the lists for recall@100 >= 0.98. `examples/ann_probe.rs` reproduces the measurement.
  The limit is memory (1.5 KB per chunk), snapshot build time and the per-file `stat`, not the dot products.
  Past the limit queries are not cheap, though: `examples/semantic_stream_probe.rs` (2026-11-17, replicated rows) measured
  steady queries at 41 ms from the snapshot at 241k chunks and 18 to 20 s streaming at 286k (30 MB against 600 MB resident).
  The streaming path re-decodes and re-tokenises every chunk; do not assume it scales like the dot product. Details in
  `docs/search-benchmarks.md`, "semantic index above the snapshot limit".
- `search_ml::embed_queries` remembers the last 32 distinct queries.
- Not done, by design: releasing the keyword index before embedding finishes. Embedding runs inside the same per-file
  loop as the exact index build and the semantic version stamp means "complete"; showing results early needs a
  product decision on what "index ready" means (partial semantic results must be labelled), not just a code change.
- **Lazy embedding (P2-3, `embed_policy.rs`, `native_index::build_or_update_corpus_index_lazy_send` / `enrich_semantic_index_send`)**: an `EmbedPolicy { limit, priority_folders }` caps how many files one build pass embeds, in order priority folder, then extension class (prose, other, code, data). Every file is still exact-indexed in the first pass, so exact search is complete while vectors are pending; "not embedded" is just "no current row in `semantic_documents`" (the state an interrupted build leaves), so no stored format or version changed. Held-back files whose exact entry is current are embedded without being re-staged. `CorpusIndexOutcome::{semantic_embedded_count, semantic_pending_count}` carry the progress; the existing entry points pass the default policy (no limit) and behave as before. Measured recall cost of embedding only a fraction: `docs/search-benchmarks.md` 2026-11-11. Test: `lazy_pass_embeds_by_priority_keeps_exact_search_whole_and_enrichment_finishes`. No UI shows the counters yet.
- `NEAR/n` filters (`near.rs`) are decided on ONE line, never across lines (a `LineHit` is one line; joining lines would change hit line numbers). Everything that reads a filter's text as search text must go through `near::terms`/`expand_terms`/`narrowing_text`/`CompiledMatchState.near`, or a NEAR filter silently matches nothing: matching pre-checks (probe = first word), index trigram narrowing, report/preview/explain highlighting. Regex mode never parses NEAR; exclude filters are plain text.
- **HTML report v2 (`report.rs`, 2026-11-17, approved mockup `.audit/report-mockup/report-mockup.html`)**: one self-contained file (a test asserts no `http://`/`https://`), still written through `ReportSink` one card per commit; CSV/JSON/JSONL untouched. Layout: masthead (banner, run time, elapsed), files-with-hits rail, KPI tiles, search-definition card, hits-by-filter bars, file-type donut, activity-by-year bars, coverage card (skips + warnings), then one `<details class="file">` card per file (hit-position strip, filter chips, OCR badge from `pdf_warning`, prev/next hit, copy path, numbered lines). **Everything that needs script is `.js-only`** (toolbar, theme, print, hit buttons; `HEAD_SCRIPT` adds the `js` class), so the report reads with script off; filter/sort/type chips/expand-collapse live in `REPORT_SCRIPT` and search each card's own text lazily (no duplicate text attribute). The dark palette is one `dark_vars!` macro used by the theme toggle and the no-script media query. Files are one flat list: path order when ungrouped, newest first when grouped by Created/Modified (the old collapsible year/month blocks are gone; the year chart and the date sort replace them). A filter keeps one colour slot (`FilterColors`, `--c1..--c6`) in its chip, bar and `<mark>` (`mark` for slot 0, `m2..m6` after); `benches/result_processing_phases.rs::bench_highlight_line` mirrors `highlight_matches` and must stay in step (its differential check compares output byte for byte; compiled, not run since the change). Coverage % is `files_searched / (files_searched + too large + unreadable + unexpected errors)` because `files_searched` leaves those out. Checked in the browser pane at 1440 wide, light and dark, on a 69-file report. Not checked: Windows, real printing (a `beforeprint` handler opens every visible card), reports above a few thousand cards.
- **Report hit gutter (`report.rs`, 2026-11-19, approved mockup in the chat of that date)**: an expanded file's code view (`.cwrap > .lines`) gets, from the one report script and only when a file opens (`setup`), a hit gutter beside the scrollbar (a coloured mark per hit, a thumb for the visible part, click to jump, hover for the line), a sticky bar (`Hit k of n · line L`), a toolbar (fold lines without hits, wrap, text size, key hints), clickable filter chips that dim a filter's hits (`.chip[data-slot]`, `.ln.hit.dim`, `mark.off`), keys `n` `p` (hits) and `[` `]` (files), a click on a line number copies `#file-N-L<line>` (opened by `openHash`), and a hit-density bar under each rail link (`--heat`, density against the densest file). **The hit highlight is not to change** (owner request): the amber `.ln.hit` row with its left bar, the gold `mark`, the bold line number and the teal `.ln.cur` outline are pinned by `the_hit_highlight_is_unchanged_and_the_code_view_has_a_wrapper_for_the_gutter`. Without script nothing is added (cards stay plain `<details>`); printing hides the gutter and toolbars. Next/previous step from the last selected hit (`d._sel`), not the hit the scroll shows (`d._i`). Look at it with `FEA_REPORT_SAMPLE_OUT=/tmp/r.html cargo test -p search-core --lib writes_a_sample_report -- --ignored`; the script's behaviour was checked in a browser, not by a Rust test.
- **`match_across_lines` (opt-in, off by default) joins a multi-word phrase over one line break** (`matching::add_cross_line_hits`/`straddles`): a second pass after the per-line loop, literal and whole-word modes only, two adjacent lines, never NEAR or typo slots. The hit is reported on the FIRST line (`match_line`, its page origin and number stay a real line's; `after` carries the rest); a pair with an excluded line is skipped. It is in the cache fingerprint, and the index trigram shortlist (`native_index.rs`) requires each word of a filter (3+ characters) instead of the whole phrase, because the break is not the phrase's space; a filter of only short words scans every file. The report/preview highlighter does not mark the second-line part. A phrase over three or more lines is not matched.
- **Saved-search alerts (`alerts.rs`, feature `neural-search`)**: a baseline file keeps two digests and one embedding, no source text. `fingerprint` and the embedding cover the sample (3 hits with context, 6 evenly spaced stored lines); `content` (`content_digest`) covers the line count, every hit and every stored line (`lines_cache`, the first `max_embed_lines`). Sample changed: `Updated` with a cosine distance. Sample same but `content` differs: `Edited` (no distance; seen even when size and modified time are unchanged). Both same but size or time differ: `Touched`. Before 2026-11-16 (projectmem #0102) only the sample was digested, so an edit outside it with the same size and time was not reported at all and a changed hit that was not one of the three sampled showed as `Touched`. Still unseen: an edit past the stored lines that touches no hit and keeps the line count, size and time. A baseline without `content` (older file) is filled in on the first check without a report. There is no materiality threshold and none should be added from the data in the repo: the one probe (2026-11-07, `alert_materiality_probe`, since removed from `search-ml/examples`; 8 + 8 hand-labelled pairs, one run) gave overlapping ranges, material 0.0162-0.3310 against immaterial 0.0028-0.0218: a clearance change from 0.001 in to 0.010 in scored 0.0162, below the largest immaterial pair. The distance stays an uncalibrated review signal until a labelled set of real revisions exists.
