# Issue 46: Windows feature-off STEP runtime qualification plan

Status: research and execution plan, 2026-10-23. No runtime qualification is claimed by this document.

## Objective and existing path

Prove on hosted Windows x64 that the native, `occt`-off path reads STEP text, builds a volume mesh, and completes a static solve. Keep this separate from the already-passed Windows executable **build** and from the later clean-machine, packaged-app acceptance gate. The built application must ultimately run offline on Windows 10 1809+ / Windows 11 without admin rights or a preinstalled runtime.

`fea-problem::Problem::from_step` selects `native_solid` when `occt` is absent. `fea-problem::solid::solid_mesh` passes its face-tagged `SurfaceSolid` to `solid-kernel::mesh_volume`, checks the 5% volume bound and refuses a named load/support face that the mesh did not resolve. `fea-problem::solve` then uses that mesh. Existing `fea-problem/tests/native_solid.rs::supports_and_loads_follow_their_faces_and_the_edited_solid_solves` already makes native STEP text, adds a side hole, meshes, loads and solves, asserting equilibrium below `1e-3` and stress above the 5 MPa applied tension. It is not an OCCT test. The current `qualification.yml` Windows matrix runs `scripts/qualify.py`, whose workspace command is `cargo test --workspace --locked -j 2 --no-fail-fast` without CAD features on Windows. Thus it may already execute the needed test; the historical phase reports did not record its focused output. Confirm actual logs before adding code or workflow steps.

The release build workflow, `.github/workflows/app-tui-build.yml`, stages `app-tui.exe` but does not run a STEP mesh or solve. Its `occt=false` branch builds without the `occt-source` feature. `.cargo/config.toml` sets `+crt-static` for `x86_64-pc-windows-msvc`; do not change that deployment invariant for this proof.

## Research and approach

[GitHub's runner documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job) says each hosted job gets a fresh VM, so a Windows run is direct platform evidence, though not proof of the oldest supported Windows build or an offline end-user machine. [GitHub's manual workflow documentation](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow) requires a `workflow_dispatch` definition on the default branch; `qualification.yml` already has one. [Cargo's test documentation](https://doc.rust-lang.org/cargo/commands/cargo-test.html) distinguishes default features from `--no-default-features` and defines `--locked`/`--offline`. Use existing workflows and tests first; add one small explicit qualification assertion only if the logs cannot isolate feature-off runtime proof.

## Execution plan

1. **Audit existing hosted evidence.** Record `git rev-parse HEAD`, current branch/status and workflow revision. Inspect the latest Windows `Workbench qualification` run at or after the native implementation commit: run conclusion, exact checked-out SHA, command, any Cargo feature flags, and the `native_solid` test line/count. Confirm `supports_and_loads_follow_their_faces_and_the_edited_solid_solves` actually ran, rather than merely compiled or being filtered/ignored. If that is clear and green at the intended source SHA, record it as the focused Windows runtime result; do not add a duplicate test or workflow.
2. **Close any evidence gap with the existing workflow.** If the previous run is missing, stale or ambiguous, run `qualification.yml` with `scope=workspace` on the qualifying branch/PR or dispatch its current default-branch revision, as appropriate. Do not dispatch a new workflow file before it reaches the default branch; use its `pull_request` trigger if a new step is needed. Keep Cargo jobs serial within the Windows job. For an explicit line of evidence, add a Windows-only `cargo test -p fea-problem --no-default-features --locked -j 1 --test native_solid supports_and_loads_follow_their_faces_and_the_edited_solid_solves -- --exact --nocapture` step to `.github/workflows/qualification.yml`, after `scripts/qualify.py`, only if the existing workspace log does not establish the test and feature set. `--exact` must select one test; a `running 0 tests` result is failure of the evidence gate even if Cargo exits 0. Capture stdout/stderr as a job log or artifact and require the test's exit code 0.
3. **Assert the actual mesh, not just a successful solve.** If the existing test output cannot show its generated mesh and admission properties, extend that same test in `fea-problem/tests/native_solid.rs` to call `solid_mesh(&p)` before `solve`, assert nonzero elements, zero inversions, named support/load surface presence, the 5% volume guard already enforced by `solid_mesh`, and `mesh.quality().with_progression(&Adjacency::new(&mesh)).acceptable(&QualityThresholds::default())` where the case presently passes. Measure the baseline first; if this model does not pass the full gate, report that distinction and choose a small supported STEP case that does without relaxing the gate. Keep the static solve and force-balance assertion. Confirm `cargo tree -e features -p fea-problem` and the CI command do not activate `occt`; inspect the test binary/dependency graph if feature unification from `--workspace` is unclear. Preserve a separate `--no-default-features -p fea-problem` focused command so the backend selection is unambiguous.
4. **Qualify at an exact source revision.** Run the focused command locally for regression and on hosted `windows-latest` x64, plus the crate's required local test set if the test or code changed. Record host `Win32_Processor` name, OS build, Rust target/triple, commit SHA, Cargo command/features, test count, tets, minimum scaled Jacobian/full gate, volume error, named surfaces, solve equilibrium, and elapsed mesh/solve time. Hardware matters because prior Windows numerical failures varied by runner CPU; one host is evidence for that host, not all hardware. If a numerical result fails only on a host, investigate the actual calculation before changing a tolerance.
5. **Check the deployment boundary separately.** The focused `cargo test` runs with Rust, Cargo and the repository present; it proves Windows native mesh/solve behavior but cannot certify the staged `app-tui.exe` on an offline clean machine. A later release gate should launch the staged feature-off executable on a clean Windows 10 1809+/Windows 11 x64 VM with network disabled, no admin rights and no installed developer runtime, then exercise a STEP import, mesh and solve through the Workbench and capture the user-visible result/log. Do not state that hosted test success satisfies this deployment gate. Keep the existing notices/release staging checks intact.
6. **Record integration and limits.** Put the exact hosted run URL, SHA, selected test output and metrics in a new append-only phase note. Update `docs/issue-46-current.json`, the readiness assessment and resume/checklist only for the Windows runtime scope actually proved. Review CodeGraph dependents and the diff if code changed. Follow the authorized forward-only branch/PR/plain-push/squash-merge flow; do not alter OCCT routing or `occt_retirement_approved`.

## Failure conditions

No Windows runtime claim if the command only builds, runs zero or ignored tests, activates `occt`, runs a cached/prebuilt binary from another SHA, lacks a completed static solve, misses named load/support surfaces, or fails the existing quality/volume/force-balance checks. Keep failures as measured evidence and fix verified root causes in their owning crate.
