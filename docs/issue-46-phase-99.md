# Issue 46 — Phase 99: persistence of the adapted-mesh store (#62)

`fea_problem::mesh_store::{encode, decode}` persist `adaptivity::MeshStore` (Phase 98) in the style of the benchmark store: a schema line, then one line per workload class holding a checksum (FNV-1a 64, accidental corruption only) and the record (key, physics and thickness, nodes, element blocks with kind, connectivity, linear elastic constants, density and name, node sets, named surfaces). Meshes with plasticity, heat data or an anisotropic material are **not written** and are counted (`EncodeReport::skipped`), so a reloaded mesh can never silently lose such data. Decoding is a trust boundary: unknown schema or an oversized text is an error; a record with a bad checksum, an unknown element kind, a dimension or connectivity mismatch, an index out of range, a non-finite coordinate or an invalid material is dropped and counted (`DecodeReport::dropped`), never repaired; entry and size budgets apply. A decoded mesh is, like a recalled one, only a starting mesh: the controller still solves and estimates on it.

Evidence (3 tests): a two-class store (Quad8 plate with thickness, Hex8 block with density) round-trips bit-exactly (nodes, connectivity, constants, names, sets, surfaces) and the reloaded block builds a `Model`; a changed coordinate (checksum), an out-of-range connectivity index with a *recomputed* checksum (structure), a negative modulus, an unknown kind, a NaN coordinate, a truncated text and garbage are dropped or refused; a plasticity mesh is skipped while its elastic neighbour is kept. `cargo test -p fea-problem -p fea-core`: 749 passed, 0 failed.

Limits: nothing in the app uses the file yet (where it lives and what is kept is the application's decision; the store is a pure encode/decode); the checksum is not an authenticity mechanism; geometry staleness is prevented only by the caller's `WorkloadKey` descriptor changing.
