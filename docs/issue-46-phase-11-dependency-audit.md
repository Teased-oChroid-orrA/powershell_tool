# Issue 46 — Phase 11 dependency decision: SHA-256 document identity

Reuse locked RustCrypto `sha2` **0.10.9** (MIT OR Apache-2.0), already present transitively in the application lockfile, as a direct feature-off dependency of solid-kernel. Registry checksum: `a7507d819769d01a365ab707794a4084392c824f54a7a6a7862f8c3d0892b283`; source <https://github.com/RustCrypto/hashes>. The locally inspected manifest declares no build script. Default features are disabled; no runtime network or native CAD library is added. Existing locked cfg-if/cpufeatures/digest dependencies are reused; no package version should change. The MIT option is elected and upstream notice is shipped at `licenses/sha2-LICENSE-MIT.txt`, copied by the existing release license staging.

STEP numeric entity IDs are local to one physical file. Hashing the exact bounded accepted source bytes provides a deterministic document fingerprint for association lookup, including across reloads. A changed byte invalidates old associations conservatively, even if the geometry appears equivalent. This is not persistent naming across edits/re-exports, geometric equivalence, authenticity or a validation certificate. No custom hash implementation, process-random hash or file-path identity is appropriate for persisted document association.
