# Issue 46 — Phase 95: STEP assemblies and placements, validated against OpenCASCADE (#51)

OpenCASCADE is now built and usable on this machine (the `occt` feature of `solid-kernel` with the prebuilt static OCCT 8.0.1 that `cadrum` downloads: `cargo test -p solid-kernel --features occt --locked --offline`: **226 passed, 0 failed, 3 ignored**; `cargo check -p app-tui --features occt --lib --tests`: clean). That gives the independent reference that the format's known ambiguity needed, so the assembly structure that `step_body::BodyContext` deliberately refuses (`NEXT_ASSEMBLY_USAGE_OCCURRENCE`, `CONTEXT_DEPENDENT_SHAPE_REPRESENTATION`, `REPRESENTATION_RELATIONSHIP_WITH_TRANSFORMATION`) is now read by `step_assembly::read`.

**The convention, measured.** A two-instance assembly (one box part, two placed usages, written around an OpenCASCADE export of the box: `examples/assembly-probe.rs`, fixture `tests/data/assembly-two-instances.step`) was read by OpenCASCADE with the two representations of the relationship in both orders and the two placements of the `ITEM_DEFINED_TRANSFORMATION` in both orders: **all four give the same placement**. OpenCASCADE does not use the written order; it decides by which placement is an item of the component's representation and which of the assembly's. The placed result is `T = Target * Source^-1`, Source the placement in the component's frame, Target the one in the assembly's: instance A (frame x' = +y, z' = +z at (10, 5, 0)) puts the 2x1x3 box on x 9..10, y 5..7, z 0..3; instance B (z' = +y, x' = +x at (-6, 3, 4)) on x -6..-4, y 3..6, z 3..4; OpenCASCADE's bounding box of the file is x -6..10, y 3..7, z 0..4, which is their union.

**`step_assembly::read(&Inventory) -> Assembly`**: for a tree-shaped assembly returns one `PlacedPart` per leaf instance (the part's `MANIFOLD_SOLID_BREP`, its definition, the usage path from the root, the rigid `Placement` into the root's frame; nested assemblies compose; one part used twice gives two instances). The rule above is implemented by membership of the placement among the representation items, so writer order does not matter. Refused with a reason, never guessed: a placement that belongs to neither or both representations, a relationship that does not join the component's and the assembly's representations, a usage without a transformation, a reference direction parallel to the axis, length units that differ between component and assembly, `MAPPED_ITEM`, a part with other than exactly one solid, a definition containing itself, several or no roots, a file with no product structure.

Evidence (macOS arm64): `tests/step_assembly.rs`, 5 tests: the placed extents of both instances (hand-derived and equal to OpenCASCADE's), the order-independence (two swaps), seven refusals, composition/inversion of placements, and the cross-check `the_native_placements_agree_with_opencascade_reading_the_same_file` (feature `occt`; bounds agree to 1e-6 after OpenCASCADE's 1e-7 padding).

Limits (not fixed): one fixture written by hand around one OpenCASCADE export (no third-party CAD system's assembly files were available); leaf parts must be single solids in the same length unit as their assembly; rigid placements only (no scale, no mirrored frames beyond what an orthonormal right-handed frame gives); `MAPPED_ITEM` / representation maps (AP214 mapped geometry) are not read; the placement is returned, not applied to the meshing pipeline (a placed body still needs the existing per-body import); persistent association across edits, healing and exact trims (the other #51 gates) are untouched; no Windows or hosted-CI evidence.
