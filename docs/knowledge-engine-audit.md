# Local knowledge intelligence engine: audit, gap analysis and roadmap (2026-11-10)

Tracking issue: #240. Source directive: `docs/MASTER DIRECTIVE- EVOLVE THIS APPLICATION INTO A LOCAL KNOWLEDGE INTELLIGENCE ENGINE.md`. Related: #238 (local ML roadmap for Search).

Scope and honesty. This is the first-stage audit the directive asks for. It was done by reading code, documentation and existing measurements, and by running a few cheap checks (network denial, existing tests). No source was changed by the audit. Numbers come only from `docs/search-benchmarks.md` and from the checks named below; anything not measured is listed under "Not measured" and is not estimated. The audit covers `search-core`, `search-ml`, `native-search` and the Search window in `app-tui`; the engineering solvers are out of scope.

## 1. Architecture map (what exists)

| Stage | Code | Notes |
|---|---|---|
| Discovery | `search-core/src/file_reader.rs` (`enumerate_files_safely`) | Walk of one root folder per run; extension, hidden-file and excluded-folder filters. No filesystem watcher anywhere in the workspace (grep for notify, fsevent, inotify: none). Freshness is a (modified, size) check on each run. |
| Extraction | `extraction.rs` (3.2k lines), `pdf_page_map.rs`, `ocr.rs`, `line_quality.rs` | Text, Office (docx/pptx/xlsx), zip (nested), rtf, pdf, many code/config formats. Scanned-PDF OCR (ocrs + rten, models bundled). PDF page provenance for citations. |

| Query understanding | `nl_find.rs`, `nl_rules.rs`, `synonyms.rs`, `neural_search.rs` | Rule-based sentence Find (no model), engineering synonym expansion, corpus-term suggestions. |

File lifecycle today: user picks a folder and runs a search or builds an index; the walk lists files; each file is extracted to lines; exact search matches lines; the optional index stores trigram and full text in `.native-search-index/` inside that folder, and the optional semantic index stores chunk excerpts and vectors in `semantic.sqlite` beside it; results carry file, line, page and citation.

## 2. Findings

### F1. The index is per searched folder, not per machine (architectural limit)
ADR-011 puts the index inside the folder it covers. Consequences: no cross-folder retrieval ("search across unrelated folder structures" is impossible by construction), every root has its own model snapshot and version stamps, and results cannot be joined across roots. This is the single biggest gap against the directive's central vision. It also has a privacy side (F6).

### F2. No relationship layer
There are no stored entities, topics, projects, folders-as-objects or relationships. Related documents are computed on demand by similarity; near-duplicate grouping exists but is not persisted. There is no evidence/confidence model and no graph invalidation. Layers C and F are partly present (semantic, cited passages); layers D and E (relationship, context) are absent; layer B (content intelligence) has entity candidates only.

### F3. No change detection beyond a rescan
No watcher; staleness is discovered at search time. Incremental indexing exists and is correct (identical-content reuse, orphan removal, OCR re-extract once), but nothing keeps an index current in the background.

### F4. Single English embedding model
MiniLM-L6-v2, 384 dimensions, English-trained. The directive asks for multilingual consideration. The model bake-off already measured bge-small, arctic-embed-xs, e5-small, gte-small and int8 variants and bge-base (see `docs/search-benchmarks.md`); none was adopted except as opt-in Refine, which is now removed. No multilingual model has been measured.

### F5. Intelligence measured and mostly negative: do not repeat
The existing evidence matters for the roadmap. On Cranfield, SciFact, NFCorpus, MS MARCO and TREC-COVID the shipped hybrid (mean nDCG@10 0.5092, Recall@100 0.724) beat dense-only (0.4657). Measured and not adopted: query-length fusion, document-level scoring, heading boost, near-duplicate removal, learned fusion, boundary-aware chunks, IVF approximate nearest neighbour, bge-small int8, two cross-encoders. bge-base rerank-rrf won all five sets but was dropped with Refine by owner decision. Any new retrieval idea must beat the current hybrid on all five sets.

### F6. Privacy and network audit (evidence)
- No HTTP/socket client in the dependency graph used at runtime. A scan of `Cargo.lock` for network-capable crates finds only `minreq` (with `rustls`, `rustls-webpki`, `webpki-roots`), pulled by `cadrum`, the OpenCASCADE binding used by `solid-kernel` behind the off-by-default `occt` feature (build-time prebuilt download). Search crates do not depend on it.
- Source grep (`TcpStream`, `UdpSocket`, `std::net`, `tokio::net`, `reqwest`, `ureq`, `http(s)://`) over `search-core`, `search-ml`, `native-search`, `app-tui`, `cli`: no network use; the one URL is a citation string in `line_quality.rs`.
- Models are `include_bytes!` in the binary (MiniLM, tokenizer; OCR models bundled). No downloader, update checker, telemetry or crash reporter found (keyword scan).
- Executed check: under macOS `sandbox-exec` with `(deny network*)` (control: `curl` fails with "Could not resolve host"), the 19 semantic-index tests, which run real embedding inference and indexing, pass.
- Gap: `.native-search-index/` and `semantic.sqlite` are written inside the user's folder and hold extracted text (excerpts) and vectors unencrypted. A folder that is synced, backed up or committed publishes that content. Not a network leak, but the directive asks to evaluate protection at rest. Logs use path redaction (`redact_paths`) in places; a full log audit is open.
- Not yet done: monitoring outbound connection attempts of the full app (not only the test binary) on Windows; the only Windows evidence is hosted CI.

### F7. Storage
SQLite for vectors and chunks with a foreign-key cascade, an `embedding_version` stamp that wipes on mismatch, `citation_version`, content hash index and `ensure_column` additive migrations: sound and reproducible from files. Tantivy has no in-place migration (outdated index is deleted and rebuilt, documented in `native_index.rs`). Vectors are stored as float BLOBs in the same table as excerpts; memory per chunk about 1.5 KB with snapshot; streaming path above 250,000 chunks. No integrity check, backup or corruption recovery beyond rebuild. No FTS5 or graph tables; SQLite can hold a relationship graph without a new database system.

### F8. Performance (existing evidence only)
Query: Cranfield (1.4k chunks) 17 ms hybrid, SciFact (5.2k) 26 ms after the snapshot (before: 172 and 638 ms). Exact search: literal 437 to 71 ms, whole word 5236 to 181 ms on 3000 files x 150 lines (this Mac, release). OCR rerun with page cache 34.7 s to 0.09 s. No measurement above ~5k chunks of corpus or above 3000 files; none for indexing throughput at 10k, 100k, 500k or 1M files; none for memory, startup or Windows.

### F9. Strengths to preserve
Exact search semantics and cited lines; deterministic fallbacks; live progress reporting (hard requirement in `CLAUDE.md`); versioned, reproducible derived data; the five-set evaluation harness (`retrieval_eval.rs`) and the "measure before adopting" rule.

## 3. Intelligence gap analysis against layers A-F

| Layer | State | Gap |
|---|---|---|
| A Filesystem | Path, size, modified, content hash (semantic index only) | No stable file id across renames at machine level, no folder objects, no version links |
| B Content | Lines, pages, entity candidates | Entities not stored or resolved; no topics, dates, project ids |
| C Semantic | Chunk vectors, hybrid ranking, cited passages | One English model; no folder/document embeddings; no multilingual |
| D Relationship | Computed similarity and near-duplicate groups | No stored edges, evidence or confidence; no versions, references, project discovery |
| E Context | None stored | Folder and neighbour context not used in ranking |
| F Knowledge | Cited passages (extractive) | Cross-file synthesis removed on purpose (Ask removed by owner); keep extractive and cited |

Note on directive part VIII (local LLM reasoning): the owner has just removed Ask and generated answers ("Search shows cited lines only, nothing generated"), after a local probe showed the bundled small model dropped a question part and invented an unsupported answer. The roadmap therefore makes multi-document answers extractive and cited first, and treats any generative step as a separate, owner-approved decision.

## 4. Benchmark and evaluation plan

Baseline already exists for retrieval (section F5, F8). Additions needed before any change, all with the existing harness conventions (datasets outside the repo, no invented numbers):
1. Retrieval: keep the five BEIR-style sets; add a cross-folder set built from the owner's representative files (private, never committed) with labelled relevant files per question.
2. Relationship: a small hand-labelled set of file pairs (same project, version, duplicate, unrelated); report precision and recall per relationship type and per evidence class (verified, metadata, statistical).
3. Version detection: pairs from real revision chains; accuracy.
4. Scale: synthetic corpus generator for 10k, 100k, 500k, 1M files measuring indexing throughput, query latency, resident memory, index size on this Mac; Windows via CI runner only as a secondary check.
5. Privacy: `sandbox-exec` network denial for the full app on macOS (extend the test above beyond the library tests); outbound-connection monitor; Windows firewall-blocked run when hardware is available.
6. Reasoning (only if a generative step is ever approved): citation correctness and hallucination rate on a fixed question set.

## 5. Roadmap

Each item lists limitation, change, expected benefit, complexity, privacy, test and rollback. Order is by priority; each phase is independently shippable and gated by the baselines above. Tracked as checkboxes in #240.

### P0: correctness, privacy, architecture
- **P0-1 At-rest exposure of in-folder indexes (F6).** Option to place indexes in the app data folder (ADR-007 vs ADR-011 revisit) with the in-folder location kept as default for compatibility; document the risk in the Index card. Complexity low. Test: index location switch keeps results identical. Rollback: setting off.
- **P0-2 Full-app offline proof.** Script and CI step running the built app's search and index flows under network denial plus a connection monitor; record result in this doc. Low complexity, no behaviour change.
- **P0-3 Integrity and recovery.** `PRAGMA integrity_check` on open for `semantic.sqlite`, rebuild on corruption with a clear message; backup not needed because everything is derivable. Low complexity.

### P1: search quality and context
- **P1-1 Machine-level catalog.** One SQLite catalog in app data listing known roots, files (stable id, path, size, mtime, content hash) and per-root index locations, built from existing per-folder indexes; enables cross-folder search and renames across roots. Medium complexity; additive; exact search unchanged. Test: cross-folder queries over two roots equal the union of per-root results; no change to single-root results.
- **P1-2 Stored entities with evidence.** Persist `entities.rs` candidates (kind, normalised value, file, line/page, extractor, confidence, class) in the catalog; entity resolution by normalisation only at first. Enables "files sharing part number X". Measure on the labelled pair set before using in ranking.
- **P1-3 Context-aware ranking, measured.** Folder and neighbour context as a small, capped prior; adopted only if it loses on none of the five sets and wins on the cross-folder set.
- **P1-5 Rarity-aware fusion.** Dense vectors wash out rare, specific terms (product ids, rare conditions); BM25 already carries idf. Test raising the keyword share when the query contains rare terms (idf above a corpus-relative threshold). Negative history to beat: query-length fusion and learned fusion. Measure on the five sets; adopt only under the rule.
- **P1-6 IDF-weighted pooling.** Weight token embeddings by idf when pooling a chunk vector so common tokens count less. `search-ml` already exposes token embeddings (used by `entities.rs`). Measure on the five sets; changes stored vectors, so adoption needs an `EMBEDDING_MODEL_VERSION` bump.
- **P1-7 Rare-term entities.** Extend P1-2 with terms whose document frequency is low and that mix letters and digits or have unusual casing (`GlowWidget`, `AX-21-7`), with the same evidence fields and class `pattern`. Shown as "files sharing a rare term"; not used in ranking until measured.
- **P1-8 Learned sparse retrieval (SPLADE) evaluation.** Needs a new model (about 100 MB) and an inverted index; evaluate size, indexing cost and gain over BM25 on the five sets before any build. Custom tokenizer vocabulary is not planned: it needs model retraining, and the lexical side already matches rare tokens as exact strings.
- **P1-4 Multilingual embedding evaluation.** Measure one multilingual small model on the five sets plus a non-English set; adopt only under the existing rule (int8 and 384 dimensions preferred; version bump handles reindex).

### P2: performance, indexing, scale
- **P2-1 Scale baselines (section 4.4)** first; no optimisation without them.
- **P2-2 Background freshness.** Opt-in watcher (notify crate: new dependency, needs approval) that queues changed paths into the existing incremental update; progress reporting preserved.
- **P2-3 Selective and lazy embedding.** Embed on demand by folder priority and extension, background enrichment with visible progress; measure recall impact.
- **P2-4 int8 vectors** (already measured as quarter memory at recall 0.995 on the ANN probe) for indexes above the snapshot limit.

### P3: relationship graph and advanced intelligence
- **P3-1 Relationship edges in SQLite** (also the base for graph-based query expansion: expand a query with terms of strongly related files; measure on the five sets plus the cross-folder set) (`relationship(src, dst, type, confidence, evidence_json, class, created, source_version)`), types FILE_IN_FOLDER, SAME_ENTITY, DUPLICATE_OF, VERSION_OF, SIMILAR_TO first. Every edge carries evidence and class; only verified or metadata edges are shown as fact; statistical edges are labelled and thresholded. Invalidated by file content hash change. Test: relationship precision and recall on the labelled set; edges must not lower retrieval metrics when used.
- **P3-2 Project discovery** by clustering over shared entities, folder lineage and similarity, shown as suggestions with evidence, never auto-applied.
- **P3-3 Version chains** from name patterns, mtime order and near-duplicate similarity; accuracy on real chains.
- **P3-4 Code intelligence** (symbols, imports) using a parser crate; evaluate need first.

### P4: discovery, answers, UX
- **P4-1 Extractive multi-document brief:** cited passages grouped by file and folder, no generation. Reuses existing evidence selection.
- **P4-2 Result explanations** extended with relationship reasons (shared entity, same folder, near duplicate) from stored edges.
- **P4-3 Related-file panel across roots** using the catalog.
- **P4-4 Knowledge gaps** (missing references) only once edges exist and precision is shown.
- **P4-5 Generative summaries or answers:** not planned; revisit only on owner request with a measured hallucination rate.

### Challenged assumptions
- A knowledge graph is justified only if P3-1 evaluation shows retrieval or navigation gains; edges that do not improve the metrics are not shipped.
- A larger embedding model or reranker is not assumed to help: Refine's win was real but cost latency and was removed by the owner; reranking returns only as an explicit opt-in with measurement.
- Visual understanding beyond OCR (diagram models) is not recommended until OCR of screenshots is measured on real screenshots.

## 6. Not measured
Scale above 5k chunks / 3000 files; indexing throughput; memory and startup; Windows performance; full-app outbound-connection monitoring; query plans and SQLite lock behaviour under concurrent write; log content audit; multilingual quality. These are baselines to establish in phase P2-1 and P0-2, not estimates.

### 2026-11-10: P2-1 scale baseline, first part (10k and 100k files; exact search and fast index only)
Method: `search-core/examples/exact_bench.rs` (release build, this Mac, disk-backed temp folder, 40 folders, 150 lines of about 12 words per file, so about 12 KB per file; synthetic text; `/usr/bin/time -l` for peak memory of the whole process including file generation). One run each, not repeated: treat differences under about 20 percent as noise. Not an SLA.

| Measure | 10,000 files | 100,000 files | Ratio |
|---|---|---|---|
| Cold full scan, sequential | 1.14 s | 24.4 s | 21x |
| Cold full scan, parallel (writes cache) | 0.45 s | 5.8 s | 13x |
| Warm re-run, result cache hit | 85 ms | 891 ms | 10x |
| Fast index build | 19.6 s | 203.5 s | 10x |
| Index narrow (walk + freshness + trigram query) | 129 ms | 1.82 s | 14x |
| Verify candidates (about 1% of files) | 9 ms | 62 ms | 7x |
| Peak resident memory (whole run) | 392 MB | 1,536 MB | 3.9x |

Reading: index build is linear (about 2 ms per file here, 10x files = 10x time). Narrowing with the index is 14x slower at 100k, and it is the directory walk (689 ms) plus the freshness check against the index (1,077 ms) that dominate, not the trigram query (7 ms): at this size an index search (1.8 s) is only about 3x faster than a cold parallel scan (5.8 s) and slower than a warm result-cache hit (0.9 s). The cost that grows with the corpus is the per-search freshness pass over every file, which a background watcher (P2-2) or a persisted directory snapshot would remove. Sequential cold scan is 4x slower than parallel at both sizes (the `parallel` default question). Peak memory 1.5 GB at 100k comes from the whole process (generation, result cache, index writer); which part belongs to search is not separated yet.

Still open for P2-1 (box stays unticked): 500,000 and 1,000,000 files (a 12 KB-per-file corpus would need 6 GB and 12 GB of the 16 GB free, so these need a smaller-file corpus or an external disk), the semantic index at scale (embedding throughput, snapshot memory above the 250,000-chunk limit), startup time, Windows, and memory attributed per stage.

### 2026-11-10: P1-1 machine-level catalog (library done; not yet wired into the Search window)
`search-core/src/catalog.rs`: a SQLite catalog (`roots`, `files`) holding each registered folder, the directory of its existing fast index, and per-file path, size, mtime and content hash. `sync_root` fills `files` from the root's own index (`all_document_metadata`) and takes content hashes from its `semantic.sqlite` when present. `search_all` opens every registered root's index and unions the hits (best score first, ties by path); a root whose index cannot be opened is skipped and named in the result. `duplicate_groups` lists files with equal hash across roots. ### 2026-11-10: P1-2 stored entities with evidence (library + catalog wiring; not yet shown in the UI; not measured)
`search-core/src/catalog_entities.rs` (feature `neural-search`, like `entities.rs`): `Catalog::index_entities` re-reads each catalogued file whose stored entities are missing or stale (stamp = size and mtime at extraction), runs the existing pattern extractor `entities::extract_candidates` and stores one row per (kind, normalised value) per file: kind, normalised value, text as written, first line, class `pattern`, extractor `pattern-v1`. Stored kinds are part numbers, materials, fastener callouts and standards; dimensions and units are not stored because they identify nothing. The loose hyphenated part-number pattern also matches dates and words, so a part number must contain a letter and a digit (`2026-11-10` is rejected). Resolution is by normalisation only (trim, collapse spaces, upper case, drop trailing punctuation): `P/N AX-21-7` and `Part number ax-21-7` are one entity, `AX-21-7` and `AX21-7` are two. Queries: `files_with_entity(kind, value)` (every file and line) and `files_sharing_entities(root, path)` (other files sharing at least one entity, most shared first, with the shared pairs as evidence). `sync_root` now upserts, so unchanged files keep their entities and a changed file loses them until re-extracted; removed files cascade. The Search window's index build records the folder and extracts entities after the "index ready" event, so extraction never delays it (first build reads every file a second time). No model score is stored (the neural category score is a per-view computation), so there is no confidence number; the class says what the row is. Tests: shared part number across two roots with line evidence and two spellings, date rejection, units not stored, no re-extraction when unchanged, changed and removed files. Not done and not measured: the labelled pair set (section 4.2) does not exist yet, so precision and recall of "shared part number means related" is unknown and nothing here may feed ranking (P1-3) or be shown as a relationship until it is measured; extraction cost at 100k files; no UI.

### 2026-11-10: P2-2 opt-in folder watcher ("Keep index current")
Dependency approved by the owner this session: `notify` 8.2 (CC0), `default-features = false` with `macos_fsevent`. Owner constraint for Windows, enforced by design: no administrator rights and nothing that modifies a system file or setting or embeds anything in the machine. `notify` uses `ReadDirectoryChangesW` on an ordinary directory handle in this process (macOS FSEvents, Linux inotify); there is no service, driver, scheduled task, registry value or file written, the watch handle closes when the watcher is dropped, and nothing is written to the watched folder. Off by default (setting 34 "Keep index current", Index tab and Options; hint says what it does). It watches only while a first build exists.

`search-core/src/watch.rs` `FolderWatcher` only collects changed paths (filtered by the walker's own rules via `file_reader::path_in_scope`: under the root, not hidden, excluded or inside the index folder). `take_quiet(2 s)` hands over a settled batch; a dropped event, backend error or more than 50,000 paths sets `overflow`, and the window then runs a normal full update. `native_index::update_corpus_index_paths_send` updates the index for just those paths through the same extraction, semantic-index, commit-replay and progress code as a full update (no directory walk, no freshness pass over every file; a changed directory contributes the files under it; a vanished path, or folder with everything under it, leaves the index; OCR setting stamp and the whole-index orphan stat are skipped because only a full update may do them). The Search window polls the watcher while idle (no search running, no build) and reuses the existing index events, so status, progress and the finished state are unchanged. Catalog recording after a delta runs the same as after a build.

Tests: `a_path_delta_leaves_the_index_equal_to_a_full_rebuild` (edit, add, delete, folder removed, folder added, excluded folder and index-folder paths ignored; result equals a fresh full build; no walk), three watcher tests with a real watcher (create/remove reported, hidden/excluded/index paths not, burst held until quiet, `restore`, missing folder is an error), `keep_index_current_updates_the_index_for_changed_files_only` (session with a real watcher: edit, add, delete reach the index), a settings test. search-core (semantic, ocr) 280 passed; app-tui lib 1282 passed.

Not verified: Windows (the Windows backend compiled only through CI later; no run on Windows hardware, so latency, network drives and antivirus interaction are unknown; hosted CI is the only Windows evidence), the GPU window drawing of the new switch (not screenshotted), and the speed gain itself: a delta avoids the 100k-file walk (0.7 s) plus freshness pass (1.1 s) by construction but no timing was taken. Limits: the watcher watches only the main folder, not "more folders"; network shares and some synced folders report nothing, so Build / update stays the way to be sure.

Numbers: `docs/search-benchmarks.md`, "rarity of words". Code left for reproduction: `FeatureSet::term_idf`, `rar-*` variants in `ranking_experiments.rs`, `examples/idf_pooling_eval.rs`. ### 2026-11-11: P2-1 scale baseline, second part (500,000 and 1,000,000 files; exact search and fast index only)
Method: as the first part, except each file has 10 lines of about 12 words (about 0.8 KB; `exact_bench <files> needlefound 10`, new third argument) so the corpus fits the disk, in the same 40 folders (12,500 and 25,000 files per folder, against 2,500 at 100k). - Index build stays linear: about 2 ms per file at every size from 10k to 1M (the cost is per file, not per byte; the 0.8 KB files cost the same as the 12 KB ones).

- The trigram query is not the problem at any size (53 to 88 ms). - Not explained: the walk is worse than linear. ### 2026-11-11: P2-1 directory-walk scaling explained (macOS vnode cache; no code change)
`search-core/examples/walk_bench.rs <files> <folders>` times, three passes each, bare `read_dir`, `read_dir` plus `metadata`, and `enumerate_files_safely` over N one-line files. Results on this Mac (8 GB RAM, `kern.maxvnodes` = 120,553), seconds:

| Files / folders | read_dir only | + metadata | enumerate_files_safely (pass 1 / 2 / 3) |
|---|---|---|---|
| 100,000 / 40 | 0.07 | 0.32 to 0.47 | 0.51 / 0.39 / 0.35 (3.5 us per file) |
| 100,000 / 400 | 0.08 | 0.30 | 0.35 / 0.35 / 0.34 |
| 500,000 / 40 | 0.4 to 2.1 | 19.9 to 23.2 | 23.2 / 21.5 / 20.7 (41 us per file) |
| 500,000 / 400 | 0.4 to 1.7 | 17.2 to 21.0 | 19.3 / 19.2 / 18.9 |

Both open hypotheses from the part-2 entry are answered: files per folder does not matter (40 against 400 folders, same time), and the cost is not a cold directory cache (the second and third passes are as slow as the first). The code is linear, one `read_dir` entry and one `stat` per file. What changes between 100k and 500k is the price of one `stat`: 3.5 us up to 100,000 files, about 40 us at 500,000 and 125 us at 1,000,000 (the earlier run). The step sits where the file count passes the kernel's vnode cache (120,553 entries here): below it every `stat` is answered from memory, above it the walk evicts as fast as it reads and each `stat` goes to the APFS catalog. Listing names alone stays fast (0.4 to 2 s for 500,000). I did not run it with a larger `kern.maxvnodes` (needs root and changes a system setting), so the vnode cache is the best-supported explanation and not proven.

Consequence: the per-search walk of a tree larger than the vnode cache costs tens of microseconds per file on macOS, which is why the fast index barely beats a scan at 500k to 1M files. It is a property of this Mac's cache size and the per-file `stat`, not of the walk code or the folder layout. No fix made. On the shipped target (Windows) `DirEntry::metadata` comes from the directory listing itself without a further call, so this cliff is not expected there; that is unmeasured (no Windows hardware; hosted CI is the only Windows evidence). The mitigation that does not depend on the platform is already built: the opt-in watcher (P2-2) updates the index from changed paths without walking, and a persisted directory snapshot would do the same for the default path. Closes the "walk scaling cause" item of P2-1; the box stays unticked for the semantic index at scale, startup time, Windows and per-stage memory.

### 2026-11-11: P3-1 relationship edges (library + labelled evaluation; graph query expansion measured negative; not wired to anything)
`search-core/src/catalog_edges.rs` adds `relationship(src, dst, type, confidence, evidence_json, class, created, source_version)` to the catalog database (created by `Catalog::init`; the table refuses an empty `evidence_json` and any class other than metadata, verified or statistical). `Catalog::rebuild_edges` recomputes every edge from `files` and `entities`; `facts_for(path)` returns only metadata and verified edges, `statistical_for(path, min_confidence)` returns thresholded statistical ones, `edges_for(path)` everything. Types: `FILE_IN_FOLDER` (metadata, 1.0, one per file), `DUPLICATE_OF` (verified, 1.0: equal stored content hash, i.e. identical extracted text; extra copies point at the smallest path; the hash of empty text is ignored so text-less files are not "duplicates"), `VERSION_OF` (metadata, 0.9 with an explicit version or copy token, 0.7 with only a status word: same folder and extension, same file-name stem after removing `v2`, `rev B`, `r3`, dates, `(2)`, `copy`, `final`, ...; groups over 30 skipped; the tiers are ordinal, not probabilities), `SAME_ENTITY` (statistical: shared stored entity, confidence = noisy-or of 1/(files holding the entity - 1); an entity in more than 25 files links nothing). `SIMILAR_TO` is not built: it needs file-level vectors from `semantic.sqlite`, whose storage is being changed (int8) by other work, and nothing here may depend on that format. Invalidation: `source_version` holds each end's stamp (content hash, else size and mtime); a rebuild deletes edges whose ends or entities are gone and rewrites edges whose stamp, evidence, class or confidence changed (`created` restarts for those, stays for unchanged edges), so a rebuild is idempotent. `sync_root` already clears a changed file's entities. Tests (`catalog_edges.rs`, `catalog_edges_tests.rs`): idempotent rebuild with identical rows including `created`; evidence present on every edge and rejected by the table when missing; invalidation on change and on deletion; facts exclude statistical edges and thresholds work; hub entity links nothing.

Labelled set (`precision_and_recall_on_a_labelled_set`, built by construction in a temp folder through the real catalog flow: 137 files, 192 edges; real Office/PDF/zip files from `search-core/test-data` included, one copied under another name; hashes are SHA-256 of extracted text set by the test because the real flow takes them from the semantic index):

| Type | Edges | Truth | Precision | Recall | What the misses and errors are |
|---|---|---|---|---|---|
| DUPLICATE_OF (pairs after closure) | 14 | 14 | 1.000 | 1.000 | 10 renames across folders, 3 same-folder copies, 1 real .docx |
| VERSION_OF | 22 | 22 | 0.864 | 0.864 | 3 false: `memoK.txt` with unrelated `memoK_v2.txt` (a limit of name matching, planted on purpose); 3 missed: versions kept in another folder (`archive/x_final.txt`), outside the same-folder rule |
| SAME_ENTITY, all | 19 | 19 | 1.000 | 1.000 | 10 identifiers in 2 files, 3 in 3 files; the "ASTM A36" standard in 33 files and a near-miss pair (`BX-21-7`/`BX-21-8`) correctly link nothing |
| SAME_ENTITY, confidence >= 0.9 | 10 | 19 | 1.000 | 0.526 | the 3-file identifiers have confidence 0.5 |
| FILE_IN_FOLDER | 137 | 137 | 1.0 | 1.0 | trivial: one per file |

Limits of this evidence: truth is planted, so the 1.0 values show that the machinery does what it is built to do, not how often real folders look like this. Real files that share an identifier but are unrelated, and real versions without a version token in the name, are not in the set; the decoys and the archive folder are the only hard cases and they cost VERSION_OF 0.136 of precision and recall. The set is not a substitute for a labelled sample of the owner's real folders (section 4.2), which still does not exist.

Under the adoption rule (lose on no set) nothing is adopted; ranking defaults and stored data are unchanged. The public sets contain no versions and (almost) no duplicates, so they cannot show what expansion over true duplicates or versions would do on real folders; that case stays unmeasured. By the rule in "Challenged assumptions" (edges that do not improve the metrics are not shipped) the module is a library with no caller: nothing in the app, indexing or ranking uses it, and it can be deleted without effect if the owner prefers; the case for keeping it is P4-2/P4-3 (result explanations and a related-file panel from facts, which need edges but not expansion). Not done: UI, calling `rebuild_edges` after index builds (cost not measured at 100k files; `SAME_ENTITY` pair generation is bounded by 25 files per entity), a labelled sample of real folders.

### 2026-11-11: P2-3 selective and lazy embedding (policy and counters built, recall measured; UI not wired)
Today a semantic index embeds every in-scope file inside the same per-file loop as the exact index (`native_index::build_or_update_corpus_index_impl`, `SemanticIndex::index_document_with_pages`); embedding dominates the cost (about 100 ms per document on this loaded Mac for the benchmark documents against about 2 ms per file for the exact index at scale). Built: `search-core/src/embed_policy.rs` (`EmbedPolicy { limit, priority_folders }`; order is priority folder in the order given, then extension class prose, other, code, data), `build_or_update_corpus_index_lazy_send` (exact index complete in the first pass; this pass embeds at most `limit` files that lack current vectors, the rest stay exact-searchable) and `enrich_semantic_index_send` (repeats passes until nothing is pending, cancelled, or a pass embeds nothing). Reuses `is_current` and the per-document transaction; "pending" is simply "no current row", the state an interrupted build already leaves, so no stored data or version constant changed and existing indexes are compatible. Held-back files whose exact entry is current are embedded without re-staging in the exact index. Progress is exposed as `CorpusIndexOutcome::semantic_embedded_count` and `semantic_pending_count` (existing outcome type; progress events and app-tui literals untouched). Default policy has no limit, so every existing entry point behaves as before. Tests: `embed_policy::tests` (3) and `lazy_pass_embeds_by_priority_keeps_exact_search_whole_and_enrichment_finishes`; `cargo test -p search-core --features semantic-search` passes (278 lib tests).

Measured (`docs/search-benchmarks.md`, 2026-11-11, random document order because the public sets have no folders or extensions): embedding time is linear in documents (25% of the documents costs 24 to 26% of the time); semantic-list-only mean nDCG@10 is 0.187 / 0.305 / 0.420 against 0.523 at 25 / 50 / 75 / 100%, Recall@100 0.190 / 0.367 / 0.552 against 0.724; a simulated union with the keyword ranking of the pending files recovers Recall@100 to about 0.68 to 0.70 and nDCG@10 to 0.39 to 0.42. So lazy embedding trades semantic recall for time one-for-one on the semantic list and should be paired with visible "n of m embedded" status; it is a start-up and responsiveness feature, not a free saving. Whether prose-first or folder-first order beats random on real folders was not measured. Not done: no UI shows the counters or starts enrichment (app-tui untouched, the Search page still builds with no limit); no settings field (the policy is an argument, to keep `SearchSettings` literals compiling); the box for P2-3 stays unticked until a caller and the status line exist.

### 2026-11-11: P3-3 version chains from stored edge evidence
New `search-core/src/catalog_chains.rs` (ungated, pure): `version_chain(path, edges, files) -> Option<Chain>` orders the `VERSION_OF` group of `path` oldest to newest from `path`'s stored edges (`Catalog::edges_for`; a VERSION_OF group is a clique, so one file's edges name every member and carry every member's tokens) and the `files` rows (mtime). `Chain { files, position, bases }`, `bases[i]` saying why `files[i+1]` follows `files[i]`: `Token` (strict token order), `Mtime` (strictly older mtime, weak), `Path` (nothing distinguishes them; path order only for determinism, weakest); `is_weak()` is true if any step is not `Token`. Tokens order the group only when every member has exactly one orderable token and all are one kind: `v` numbers compared numerically per dotted part (`v2` < `v10`, `v1.5` < `v2`), `rev`/`r` numbers, `rev` letters (A < B < AA), dates (`yyyy-mm-dd`, `yyyymmdd`, month and day range checked), copy ordinals (`(2)`, `copy of 3`). Status words next to an orderable token are ignored. Otherwise (mixed kinds such as `v2` with `rev B`, a member without a token, only status words, two orderable tokens in one name, an unplaceable token) the whole group is ordered by mtime and labelled weak. Equal tokens fall to mtime, then path. `None` for a path with no VERSION_OF edge or a group over `MAX_VERSION_GROUP`. No new tables or edge types; `catalog_edges::is_status_word` became `pub(crate)`.
Limits: a tokenless original (`spec.txt` next to `spec v2.txt`) is not assumed oldest, so that common pair is mtime-ordered and weak; "oldest to newest" is what names and times suggest, not content proof (copying and syncing rewrite mtimes); nothing consumes the chain yet (preview and `explain` unchanged).

### 2026-11-11: NEAR/n word-distance queries (`torque NEAR/5 bolt`)
Built: a filter of exactly `word NEAR/n word` (`NEAR` in any case, n >= 1, both words alphanumeric) matches a line that holds both words at most n word positions apart, either order (`NEAR/1` = adjacent), any pair of occurrences counting; the same word twice needs two occurrences. Parser and matcher are `search-core/src/near.rs`; `matching.rs` decides the filter slot with it (`CompiledMatchState.near`), so plain, whole-word, accent-folding and every match mode (any line, all in file, proximity, `;` groups) work unchanged and plain queries take the old path. Words are the typo matcher's alphanumeric runs; a term hits a word as a substring (whole word in whole-word mode) after lowercasing/folding, the same rules as a plain filter. Every other reader of filter text was routed through it, or a NEAR filter would silently match nothing: the cheap pre-checks use the first word as a probe, the index trigram narrowing uses the longer word (otherwise the `near/5` trigrams dropped real matches), and the report, TUI preview and match explanation highlight both words. The query preview and Run view name the mode (`[any line; NEAR: within 5 words, same line]`), and the Find help has a row for it. Per-file progress reporting is untouched (the change is inside per-line matching).
Scope decision: same line only. A `LineHit` is one line and the extractors give paragraphs (DOCX), one line per PDF content stream and physical lines in text files; joining lines would change hit line numbers and the context shown. Evidence is the line model in `matching.rs`/`extraction.rs`, not a measurement.
Tests: `near::tests` (parse accept/reject, boundary n and n+1, order, multiple occurrences, same word, punctuation, substring vs whole word, case, accents) and `matching::tests::near_*` (boundary, no cross-line joining, whole-word, fold, mixed with plain filters, AllInFile, groups, regex-mode inertness, plain/literal `NEAR` text unchanged, typo tolerance ignored); app-tui `group_label_names_near_queries_but_not_in_regex_mode`, `a_near_query_highlights_both_of_its_words`. `cargo test -p search-core --lib --tests` 244 + 10 passed; `cargo test -p app-tui --lib search` 266 passed. Plain `cargo test -p search-core` also builds examples, and `semantic_scale` / `edges_cost` do not compile without their features (errors in files not touched here); not investigated.
Limits: one operator with two single words (no phrases, no chains, no `C#`-style terms; such text stays a plain filter); no NEAR in regex mode or in exclude filters; no typo tolerance on NEAR words; highlighting marks every occurrence of both words on the line, not only the close pair; the index narrows on one word only; not screenshotted, not run on Windows, no timing measurement of the per-line word split on very long lines (PDF streams).

### 2026-11-12: P3-2 project discovery (suggestions only)
Built `search-core/src/catalog_projects.rs` (`discover`, `Catalog::project_suggestions`; reads stored files, roots and edges, writes nothing). A candidate is a folder strictly below a registered root with at least 3 files in its subtree whose largest connected component holds at least 60 % of them; files link through `VERSION_OF` edges and `SAME_ENTITY` edges of confidence at least 0.19 (an identifier held by at most six files). Duplicates are not used (copies cross project boundaries). Selection is top-down (the shallowest folder that passes, nothing below it), skipping a folder whose only content is one child folder; at most 12 are returned. Evidence is the stored identifiers that link most files plus a count of versioned files, never generated. The Search window has a Projects popover (`SearchAct::FindProjects` reads the catalog on a blocking thread, `SearchAct::UseProject(i)` sets the folder to search); nothing is looked up until the button is clicked and nothing changes until a suggestion is clicked. No network, no new dependency, no stored data or schema change.

Precision, measured two ways (labels are mine; neither is a real user's files):
- Labelled synthetic tree (`catalog_edges_tests::project_discovery_precision_and_recall_on_a_labelled_tree`, real index, entities and edges): 10 true projects (two under one `old/` folder, each with doc/ and data/ subfolders, every file also citing one common standard) and three decoys (an inbox of unrelated files, a folder of one-off identifiers, a folder whose 6 files all cite one standard). 11 suggested, 10 of 10 true projects found: precision 0.91, recall 1.00. The one false positive is the decoy whose files all cite one standard; it is a genuinely linked cluster, so no signal here separates it from a project. The inbox, the one-off-identifier folder, the `old/` wrapper of two projects, the root and project subfolders were never suggested. The first run with the confidence bar at 0.5 (the preview note's bar) suggested nothing (recall 0): identifiers held by 4 to 5 of 7 files give edges of 0.25 to 0.33, so the bar had to drop; 0.19 was set once from the "at most six files" rule, then 0.19 and the 6-file decoy interact (at exactly 0.2 floating-point rounding dropped the decoy, so the boundary is fragile).
- This repository's own docs, Rust and TOML (`examples/projects_eval.rs`, 795 files in `docs`, `src`, `fea-core`, `lug-solver`, `bushing-solver`; 13,575 edges): five suggestions, `docs` (304 files, 88 % linked), `fea-core` (173, 88 %), `lug-solver` (38, 84 %), `bushing-solver` (15, 80 %) and `src` (265, 91 %). The first four are real units with sensible evidence (type names such as `ModulusScale`, `FiniteLug`, `ToleranceRange`, and for docs `WinUI`, `issue-46-abc-and-retirement`). `src` is an artefact of my copy (`app-tui/src` and `search-core/src` merged into one folder by rsync), so it counts as wrong for this tree although both crates are real: 4 of 5 by hand. Recall is not defined without labels, but sub-units (a toolbox folder inside `app-tui`) were never found: a folder that passes at the top hides everything below it.

Reading and limits: precision is acceptable on both trees, so it ships as suggestions only. The weakness is granularity, not wrong folders: top-down selection returns broad folders on a real tree; finer suggestions would need a different cut (for example the deepest folder that passes) and a labelled real corpus to choose between them, and no such corpus of mixed engineering folders is available here. Entities of code files are identifiers, so the evidence reads as type names rather than part numbers; for engineering folders (part numbers, standards) it reads as in the synthetic tree, unmeasured on real ones. A folder of documents that all cite one standard is suggested as a project (known false positive). Thresholds (3 files, 60 %, 0.19) are not tuned beyond the two trees above. Suggestions come from the whole machine catalog, across roots, and cost one read of every catalogued file and linking edge when asked (not measured at 100,000 files). The native window was rendered (`search_snapshot`, "search-projects"); the terminal toolbox has no Projects view.

### 2026-11-12: P4-4 knowledge gaps (hints only, shown on request)
Built `search-core/src/catalog_gaps.rs` (`find`, `Catalog::knowledge_gaps`; reads stored files, standard and part-number entities and `VERSION_OF` edges, writes nothing). Two kinds, both from what the catalog already stores:
- Missing document: a `standard` entity (ASTM, AMS, MIL-STD/DTL/PRF, NAS, ASME, SAE) cited by at least 2 files while no catalogued file name contains it (compared letters and digits only, case-folded, so `ASTM A36` meets `astm_a36_spec.pdf`). Reads "cited in n files; no file name contains it".
- Dropped identifier: a version group of at least 3 files ordered by explicit version tokens only (every step `Basis::Token`, so mtime-only or status-word groups claim nothing), whose newest member lacks a standard or part number that every earlier member holds, and whose text was read (it has some stored entity). Reads "in all n earlier versions, not in the newest, <name>".
Not built: "entity mentioned in one file only". Most identifiers occur once by nature (the labelled tree's own one-off ids, any log), so the signal has no contrast and cannot be given a precision worth showing.

The Search window shows them in a second card under Projects, "Possible gaps", behind a "Look for gaps" row (nothing is read until clicked). Rows have no action; nothing filters, ranks or hides anything, and the card says the hints can be wrong. No network, no dependency, no schema change.

Precision (labels are planted by me; neither tree is a user's folders):
- Labelled tree (`catalog_edges_tests::knowledge_gaps_precision_and_recall_on_a_labelled_tree`, real index, entities and edges): missing documents, 5 flagged, 4 true (4 standards cited by 3 files, none filed): precision 0.80, recall 1.00; the error is a standard whose document exists under a name without its number (planted, unavoidable by name matching). Standards whose document is present in any spacing or case, and one cited by a single file, were not flagged. Dropped identifiers, 5 flagged, 3 true: precision 0.60, recall 1.00; the two errors are renumberings (old id replaced by a new one), which look identical to a loss. Not flagged, correctly: unchanged chains, a chain whose newest file has no text, an identifier held by only two of three earlier versions, a status-word (mtime-ordered) group. The 0.60 depends on how many renumbered chains I planted (2 against 3 true drops); a real ratio is unknown.
- Real files (`examples/gaps_eval.rs`; `docs`, `fea-core`, `lug-solver`, `bushing-solver`, `app-tui/src`, 767 files): nothing flagged anywhere. Only 6 files in these trees cite a standard (each standard in one file, or three citing files with their own docs), and none has explicit-token version groups with identifiers. So there is no false positive on real files, and equally no evidence of recall: engineering folders with many documents citing standards and revision-named files are exactly what is missing here.

Reading and limits: shipped as hints because a note that can be ignored costs little and the planted false positives are the kinds a reader recognises at once (the evidence names the files). Precision on real engineering folders is unmeasured; the dropped-identifier kind is the weaker (0.60, renumbering is common in real revisions), and if a labelled real folder shows it below roughly 0.5 it should be removed first. Missing-document matches names only, so a document filed under a descriptive name is reported as missing; a standard legitimately kept outside the indexed folders always is. The native window was rendered (`search_snapshot`, "search-projects"): the Projects popover shows a collapsed "Possible gaps" section below Possible projects with no layout change; the expanded gaps card was not screenshotted (only its rows were checked in `gap_hints_wait_for_a_click_and_never_change_anything`). The popover's header text still describes projects only.
