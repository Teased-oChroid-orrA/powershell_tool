# Issue 46 — Phase 79: hexahedron-to-tetrahedron transition and the pyramid decision (#56)

**Decision: no `Pyramid5` element.** A pyramid over a quad face is two tetrahedra, so every hex–pyramid–tet or quad–tet transition reduces to one question: which diagonal does each shared quad take. The Phase 78 rule (the diagonal containing the smallest of the quad's four global node numbers) answers it for any element that owns that quad. A pyramid element would add an `ElementKind` arm everywhere (shape functions, quadrature, quality, conformity and face tables, rational/non-polynomial interpolation) and would still need the tetrahedral side to match the quad's triangulation. The cost is not justified by any capability the diagonal rule lacks.

`meshing::transition::tetrahedralize(mesh, select)` converts selected `Wedge6` **and `Hex8`** elements into `Tet4`; `tetrahedralize_wedges` keeps its wedge-only behaviour. `interface_diagonal(quad)` publishes the rule: a tetrahedral region built elsewhere (a boundary-constrained mesher) meets a converted element conformingly when its triangles on the shared quads use that diagonal.

Hexahedron split: its six quad faces take the rule's diagonals, giving one of 64 bit patterns, of which the rule produces 42. A table for all 64 patterns is found once by exact search over the 70 candidate tetrahedra of the reference cube and validated exactly (integer volumes add to the cube's, interior faces pair with opposite orientation, unmatched faces lie on the cube surface). Every pattern the rule produces tiles with 6 tetrahedra and no extra nodes. A Python pre-check and the Rust exhaustive test agree.

Refusals: a selection that separates two elements (wedge or hexahedron) sharing a quad face is an error naming the face; second-order hexahedra (`Hex20`/`Hex27`, only when hexes are being converted) and `Wedge15` are refused (orders are not mixed); a non-positive scaled Jacobian after conversion is an error.

Evidence (macOS arm64, `cargo test -p fea-core --locked --offline`: 514 passed, 0 failed; 9 transition tests): **all 40320 numberings** of a unit cube's eight nodes split into positive tetrahedra of total volume 1 whose triangles on every face meet along the rule's diagonal (42 distinct patterns); a 3x3x3 hexahedral block converted entirely is volume-exact, passes `check_conformity` and the linear patch test to 1e-10; a converted `Hex8` meets an independently built six-tetrahedron cell (Kuhn split around a diagonal from an endpoint of the rule's diagonal) with every interior face used twice, while the same cell built from the other diagonal is detected as cracked (negative control).

Defect found (not fixed here): `adjacency::check_conformity` cannot see two blocks that triangulate a shared quad differently, since both triangulations look like exterior boundary. Phase 78's conformity assertion alone could not have caught a wrong diagonal (its patch test does). The new test counts faces against the known exterior instead. A general fix needs a notion of the intended exterior.

Limits: first order only; the tetrahedral side must be built to the rule (no mesher in this tree does that yet, so a real hex-region/tet-region part still needs a boundary-constrained tetrahedral mesher such as `solid-kernel` PLC recovery fed the hex region's triangulated boundary); no quality-driven choice of where to transition; contact tags and plasticity history are not remapped; the registry (`compatibility.rs`) gains no strategy because `GeneralHybrid3d` is still unavailable; no Windows or hosted-CI evidence.
