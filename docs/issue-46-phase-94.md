# Issue 46 — Phase 94: erratum to the Phase 79 pyramid decision, and the measured cost of a hex-tet node tie (#56)

**Erratum.** Phase 79 said the diagonal rule covers "every hex-pyramid-tet or quad-tet transition" and so no `Pyramid5` is needed. That holds only when the hexahedra next to the tetrahedra are *also converted*: then both sides of every interface quad are triangle pairs. It does **not** hold for an *unconverted* hexahedron meeting tetrahedra: the hexahedron's face is a quadrilateral and cannot be changed, the tetrahedra's face is made of triangles, and no choice of diagonal makes them the same face (the converted-region interface check of Phase 79 correctly refuses exactly that selection). A face-conforming interface between a kept hexahedron and tetrahedra needs a quadrilateral-to-triangles element (a pyramid) or a non-conforming tie. The Phase 79 conversion, its tests and its other conclusions stand; only the sentence of the decision that generalised past converted regions was wrong.

What the kernel can do today, with evidence:
1. **Convert whole regions** (Phase 79): a hexahedral block becomes tetrahedra with the rule's diagonals; conforming.
2. **Wedge layer** (Phases 78, existing sweeps): hexahedra and wedges share quadrilateral faces directly, wedges and tetrahedra share triangular faces; so an extruded model transitions hex -> wedge -> tet with existing elements.
3. **Node tie** (`meshing::weld::merge`, already the way the 2D hybrid mesher joins structured and unstructured regions): the four nodes of the interface quad are shared; the hexahedron's face stays one bilinear quadrilateral and the tetrahedra's two triangles. This is node-conforming and not face-conforming (face counting sees both as boundary; `check_conformity` cannot judge it). `tests/hex_tet_tie.rs` measures it:
   - linear patch test across the tie: worst error **2.6e-18** over 63 interior nodes, 9 of them on the interface (a linear field is reproduced exactly: bilinear equals linear on a planar quad);
   - cantilever tip deflection, left half hexahedra, right half tetrahedra from the same grid: 8x2x2 grid all-hex -0.2283, tied -0.2171 (-4.9 %), all-tet -0.1403 (-38.5 %); 16x4x4 all-hex -0.2531, tied -0.2479 (-2.1 %), all-tet -0.2118 (-16.3 %). The tied mesh sits between the all-hex and all-tet answers and much closer to the all-hex one; the loss is the linear tetrahedra's bending stiffness, which the tie does not add to. The tie's own contribution (the interior mismatch of a bilinear against a two-triangle face, second order in the face size) is below what these meshes can resolve.
4. **Pyramid5** would give a face-conforming interface and is the clean answer for general unstructured hex-tet; it is not built. Cost: a new `ElementKind` arm in shape functions, quadrature (apex), quality (the apex Jacobian is zero by construction), stress recovery, topology/faces, import/export and the derivative kernels; and, more to the point, it would still need a tetrahedral mesher that accepts the pyramid layer's triangular sides as given boundary facets, which the tree does not have (`plc_conform` splits facets with Steiner points, so interface triangles could be subdivided). Without that mesher a pyramid element has no producer here. Recorded as the product decision it is: build the element together with a facet-preserving tetrahedral mesher, or keep the node tie and the wedge route.

Evidence: `cargo test -p fea-core --test hex_tet_tie` (1 test, passes in debug and release).
